# TowerPulse — Live Run Evidence & Proof of Work

This document is a companion to the main [README.md](./README.md). It exists for one reason: **to show that this pipeline was actually built and run**, end-to-end, on a real local cluster — not copied, not simulated, not just described.

Every screenshot below is from a single unbroken run on **July 26, 2026**, captured directly from my own WSL Ubuntu terminal and the Spark UI. Nothing here is a mockup.

---

## Why this document exists

Anyone can write a README describing an architecture. What's harder to fake is:

- A terminal session with a real hostname, real system clock, and real command history
- Source code visible via `cat`/`:load` inside a live REPL, not pasted into a text editor
- A Spark UI reporting real uptime, real batch counts, and a real job ID that increments over time
- Output that only exists if Kafka, Spark Structured Streaming, watermarking, and windowing are all actually wired together correctly

The sequence below walks through the run in order, so you can follow the same logic I did.

## 1. Environment — real local machine, real date

Everything runs on WSL Ubuntu 24.04.3, on my own machine, not a cloud notebook or borrowed sandbox.

`start-dfs.sh` brings up a real local single-node HDFS cluster (NameNode + DataNode + SecondaryNameNode) — this is the foundation every later layer reads from and writes to.

## 2. Kafka topics created live

```
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic telecom_cdr
```

## 5. Real debugging, not a scripted demo

![Load vs run debugging](./images/05_debugging_load_vs_run.png)

Loading a Scala object with `:load` only *defines* it — it doesn't execute `main()`. `spark.streams.active` returning `Array()` twice, before finally calling `TowerPulse.main(Array())` to actually start the query, is exactly the kind of small real-world debugging step that shows up when you're actually operating a system live, not reciting a rehearsed script.

## 6. Streaming query live — continuous micro-batches

![Streaming query live](./images/06_streaming_query_live.png)

Once `main()` runs, Spark starts executing micro-batches continuously (`Stage 1`, `Stage 27`, `Stage 149`, `Stage 201`...) — the stage counter keeps climbing for as long as the query runs, because Structured Streaming queries never terminate on their own.

## What this proves, concretely

- The 5-layer architecture in the README is not aspirational — Layer 4 (Spark Structured Streaming) is shown running live, end-to-end, above.

- The dual-sink pattern (Parquet + Kafka) is real, verifiable from the source code screenshot.
- This was operated, debugged, and monitored by one person, in one continuous session, on one local machine.
